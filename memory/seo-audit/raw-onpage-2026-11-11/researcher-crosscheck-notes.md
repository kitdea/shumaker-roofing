# Researcher cross-check notes — on-page crawl (2026-11-11)

**IMPORTANT — read this before using anything in `sitemap-inventory.json` or `non-sitemap-links-tested.json` in this folder.**

When I (researcher) started this task, `memory/seo-audit/on-page-crawl-2026-11-11.md` already existed, authored by **web-designer-dev**, who ran a real HTTP crawl (`requests`/`BeautifulSoup`, `crawl.py`/`analyze.py` in this same folder) against the live site — actual status codes, actual meta descriptions, actual canonical tags, actual HEAD-checked images. That is a materially more reliable method than the one available to this profile (a third-party text-extraction API, no raw HTTP/browser access).

I built my own independent crawl anyway (files `sitemap-inventory.json`, `non-sitemap-links-tested.json`, this folder's `sitemap.xml`) before discovering the collision, and it is **preserved here for the audit trail**, but two of my "Critical" findings do **not** hold up against web-designer-dev's ground truth and must not be relied on:

1. **"5 service pages have no H1"** (chimney-maintenance, commercial-flat-and-low-slope-roofing-restoration, gutter-installation, residential-roofing, roof-installation) — **contradicted**. web-designer-dev's real crawl found exactly one H1 on all 53 pages except one blog post (which has two). I checked their raw `crawl_raw.json` directly: it parses real HTML and shows these pages do have H1s.
2. **"4 service pages link out to pre-migration/legacy URLs not in the sitemap, and one of those resolves to what looks like the old pre-June-2026 site"** — **contradicted**. web-designer-dev's crawl found 0 pages with internal links missing from the sitemap, and I grep'd their `crawl_raw.json` directly for the exact stale-slug strings I found (`roof-repair-in-frederick-md`, `meet-the-shumaker-roofing-team`, `do-commercial-silicone`, `roofing-company-in-frederick`) — **zero matches**. The live HTML, fetched via real HTTP today, does not contain these links.

**Conclusion:** my extraction tool (a keyless third-party "Exa" backend, per its own error messages) served me **stale/cached content** for at least 4 of the 13 service pages, not what's actually live now. This is consistent with other reliability problems I hit from the same tool during this session: HTTP 429 rate-limiting on 3 separate fetches, two different fetches of the identical `/privacy-policy` URL returning two different `<title>` values and two different bodies, and 6 URLs returning only nav/footer boilerplate on every attempt. **Do not treat any single-source finding from this raw data as confirmed without cross-checking against web-designer-dev's `crawl_raw.json`/`url_inventory.csv`, which used real HTTP and should be treated as the ground truth for this site's on-page/crawl state.**
